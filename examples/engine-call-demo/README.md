# engine-call-demo — calling an engine function the framework doesn't wrap

s2script's entity API covers **state** thoroughly: `EntityRef` can read and write any field, through
pointer chains, with liveness gating. What it historically could not do is call a **function** the
core hadn't already wrapped. Every engine call — `respawn`, `switchTeam`, `terminateRound` — had to be
signature-resolved and exposed by the framework, so "the core doesn't wrap X" meant waiting for a
release.

This example declares its own engine call and uses it. It burns a player by calling
`CBaseModelEntity::Ignite` directly, and it deliberately includes a **second descriptor that is
supposed to fail**, because the interesting property here isn't that a good descriptor works — it's
that a bad one is caught by name instead of silently misbehaving.

```
sm_ec_status        report every declared call and why it is (or isn't) available
sm_ec_burn <target> set a player on fire for 10s
```

## The three files

```
gamedata/plugin.gamedata.jsonc   what to call, and how to find it on THIS build
package.json                     s2script.gamedata + s2script.permissions
src/plugin.ts                    Engine.call("ignite") -> a typed, plain callable
.s2script/gamedata.d.ts          GENERATED by `s2s build` from the gamedata
```

### 1. Declare it in gamedata

Engine addresses move every CS2 update, so they belong in regenerable data, never in code — the same
rule the framework follows for its own `gamedata/core.gamedata.jsonc`. A plugin's gamedata uses that
identical shape: a named entry keyed by **platform id**, details nested inside.

```jsonc
"signatures": {
  "CBaseModelEntity_Ignite": {
    "linuxsteamrt64": { "module": "libserver.so", "pattern": "55 48 89 E5 …", "resolve": "direct" }
  }
},
"calls": {
  "ignite": {
    "receiver": { "kind": "entity" },
    "target":   { "kind": "signature", "name": "CBaseModelEntity_Ignite" },
    "args":     ["float", "int", "entity", "float"],
    "argNames": ["flFlameLifetime", "nFlags", "pAttacker", "flSize"],
    "returns":  "void"
  }
}
```

`args` is the marshalling contract the runtime uses. `argNames` is documentary — the runtime never
reads it — but it's what makes the generated signature readable.

### 2. Declare the permission

```jsonc
"s2script": {
  "gamedata": "gamedata/plugin.gamedata.jsonc",
  "permissions": ["engine:calls"]
}
```

A `calls` section without this **fails the build**. That's deliberate: the capability should be
visible in the manifest before anyone installs the plugin.

### 3. Call it

`s2s build` generates `.s2script/gamedata.d.ts` from your gamedata, so the call is fully typed:

```ts
ignite: (self: EntityRef, flFlameLifetime: number, nFlags: number,
         pAttacker: EntityRef | null, flSize: number) => void;
```

```ts
const ignite = Engine.call("ignite");   // a plain callable, or null

if (ignite && pawn?.isValid) ignite(pawn.ref, 10.0, 4, null, 0.0);
```

Resolve once at load and null-check there. An undeclared name is a `TS2345`, a wrong argument count a
`TS2554` — the same gate that checks the rest of your plugin.

## Why it's safe enough to ship

**No raw pointer ever reaches JavaScript.** Your code holds a descriptor *name*. Core holds
`(index, serial)` pairs. Only the shim holds pointers. A call whose receiver went stale degrades to a
no-op; a call that *returns* an entity converts the returned pointer to a handle and runs it through
the same books-gated path `Pawn.forSlot` uses, so a bogus pointer yields `null` rather than a live
reference to freed memory.

**A vtable index is never trusted bare.** A signature either matches this build or it doesn't — it
self-validates. A borrowed *index* doesn't, so any `kind: "vtable"` target **must** carry a
`validate.prologue`, and the build refuses one without it. The negative descriptor in this example
shows why: it names the `CCSPlayer_ItemServices` slot that other frameworks' gamedata calls
`DropActivePlayerWeapon`, but on this build that slot is a `GiveNamedItem` **thunk**. A thunk is
valid, in-range executable code, so a `.text`-range check *passes* it — calling through would hand an
entity pointer to a `const char*` parameter and misbehave silently. Only the prologue tells them
apart. On load you'll see:

```
WARN: [engine-calls] '@demo/engine-call' call 'dropActiveWeaponRejected' unavailable:
      prologue mismatch (resolved slot is not the intended function)
[engine-calls] '@demo/engine-call' armed 'ignite' (call id 0)
```

One descriptor degraded, the other armed. **Degradation is per-descriptor**, never per-plugin.

**The operator has the final say.** Declaring the permission isn't enough. Until your plugin id is
listed in `addons/s2script/configs/permissions.json`, every declared call resolves to `null`:

```jsonc
{ "engine:calls": ["@demo/engine-call"] }
```

Omit it and the plugin still loads and runs — just with its calls degraded. An operator's oversight
can't take a server down.

## Running it

```bash
cd examples/engine-call-demo && npx @s2script/sdk build
cp dist/_demo_engine-call.s2sp <server>/addons/s2script/plugins/
# add "@demo/engine-call" under "engine:calls" in addons/s2script/configs/permissions.json
```

```
] sm_ec_status
[engine-call-demo] ignite: available
[engine-call-demo] dropActiveWeaponRejected (expected to fail): prologue mismatch …

] sm_ec_burn @all
[engine-call-demo] called ignite on 2 pawn(s); entityflame 0 -> 2 (EFFECT CONFIRMED)
```

### Why the reply counts entities

`sm_ec_burn` could just say "called ignite on 2 pawns" — but that would only prove a call was
*dispatched*. A declared call that resolves and receives a **wrong argument** returns cleanly and does
nothing at all. Two real ways that happens here:

- **`nFlags` missing bit `0x4`.** Ignite then consults an "is this ignitable?" virtual, which is false
  for every player pawn, and returns having done nothing.
- **A float that doesn't arrive.** The framework had exactly this bug during development: the invoke
  thunk declared its float registers as `double`, and since SysV passes a 32-bit float in the *low*
  32 bits of the register, `10.0` arrived as `0.0f`. No crash, no diagnostic — just a burn with zero
  duration.

Both look identical from the caller's side. `Ignite` spawns one `CEntityFlame` per victim, so a rising
`entityflame` count is independent evidence the *engine* acted. If you write plugins on this API,
**measure an effect, not a return value** — and if you're checking a float landed, check that its
effect *persists* (flames alive after 4s, gone by 12s, for a 10-second burn).

## What you own by using this

Your gamedata is your treadmill. When CS2 updates, that byte pattern will stop matching and your call
will degrade with a named reason — the plugin keeps running, the feature stops. Re-deriving it is your
job, not the framework's.

Resolve engine facts against **your own** binary rather than copying a constant from another project.
`docs/re-strategy.md` is the doctrine; `docs/re-notes/2026-07-24-ignite.md` records how every value in
this example's gamedata was derived and how to re-derive it, including the parts that were wrong in
the first attempt.

## Limits (v1)

The receiver is always an entity — `receiver.kind` is a tagged field so other receiver kinds can be
added later. Args come from a closed set (`bool`, `int`, `float`, `string`, `vector`, `entity`) and
returns from `void`, `bool`, `int`, `float`, `entity`. At most **5 integer-class args and 8 float
args** — `this` occupies the first integer register, and everything except `float` is integer-class,
so this isn't a flat "6 arguments" rule. No struct-by-value, no out-params, no `string` returns.

And this is **calls only**. Plugin-declared *hooks* remain core-owned.
