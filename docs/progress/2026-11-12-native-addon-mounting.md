**Native addon mounting (2026-11-12) — offline; live acceptance pending.** Prompted by the Nov 11 CS2 update breaking MultiAddonManager (it is compiled against the same `INetworkMessages` layout that crashed s2script), which took custom UI and sounds off Gabriel's server. s2script now mounts workshop addons and pushes them to clients itself. The shim (`shim/src/addons.cpp`) mounts VPKs into the "GAME" search path through a slot-pinned `IFileSystem` (`IFileSystem_vtableSize` 128), detours `CHostStateMgr::SetPendingHostStateRequest` so every map load carries the extra addons after the map's own one, and runs the client handshake: `CNetworkGameServerBase::ReplyConnection` (detour, pre/post swap of `m_szAddonName`) names the first addon a client lacks, a reconnect inside the timeout marks it downloaded (from `OnClientConnected`), and a checked global hook on `CServerSideClient::SendNetMessage` (slot 16) turns the next `CNETMsg_SignonState` into a CHANGELEVEL naming the next addon. A client still on its first addon after the connect timeout is kicked on the next frame. Every piece is gated by its own gamedata (two signatures with string-xref validators, six offsets, one pin) and stays inert until a plugin configures something, so a server still running MultiAddonManager sees no change. `@s2script/sdk/addons` exposes it (one owning plugin; its unload unmounts everything), and the new base plugin `addonmanager` takes MultiAddonManager's settings (`addons_extra`, `addons_client_extra`, the timeouts, cache and disconnect-message options) plus `sm_addons*` admin commands. Not ported from MAM: the vscript `GetAddon` override, HLTV clients, and re-sending a SignonState to clients already in game when a client addon is added (they get it on their next connect). MultiAddonManager (GPL-3.0) was read as a behavioural reference only; no code was copied.
