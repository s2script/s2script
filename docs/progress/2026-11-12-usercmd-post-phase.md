**Usercmd post phase (2026-11-12) — offline; live acceptance pending.** Prompted by replay recording (EdgeGamers' 3D round replays, surf timers' replay recorders), which needs each player's state after every command, the way ModSharp plugins get it from `PlayerRunCommand.InstallHookPost` (Source2Surf/Timer's `ReplayRecorderModule.OnPlayerRunCommandPost`). `clients.onRunCmd(handler, { phase: "post" })` and the `OnPlayerRunCmdPost(cmd, info)` export now run once per command the server actually ran, after its movement was applied and written back to the pawn; `"pre"` stays the default and is unchanged. The pre phase hooks the batch entry (`ProcessUsercmds`), which sees every command before any of them runs, so post needed its own engine point: `CPlayer_MovementServices::RunCommand` (new core gamedata `PlayerMovementServices_RunCommand`, ModSharp's pattern, unique on builds 26598758 and the Nov 5 one; vtable slot 26 of `CPlayer_MovementServices_Humanoid`, checked by index, with `CCSPlayer_MovementServices` overriding slot 26 with a guard that tail-jumps to it). It is a checked KHook binding installed lazily on the first post subscriber, like the pre one, and the pre install is now per channel too (it used to test whole-store emptiness, which a post subscriber would have defeated). In post the command is read-only twice over: the shim's post frame has no mutable command and core's write natives no-op (a debug build warns once); the handler's return is ignored and does not truncate other subscribers. `info` is `{ slot, tick, commandNumber }` (server tick from the globals, `legacy_command_number` from the command). The view and one `info` object per subscriber are reused; core passes no arguments and reuses a version-cached subscriber list, and a steady-state post dispatch makes no Rust allocation at all (a test counts them). Getting there fixed two allocations every fan-out in core paid per subscriber call: `Registry::is_live` built a `String` key for each liveness check (`LiveTable::is_live` now takes a borrowed key), and `ParentBusy` copied the owner id into a fresh `String` (its stack now reuses popped entries). `UserCmdView` gains read-only `pressedButtons` / `changedButtons` / `scrollButtons` (`CPlayer_MovementServices::m_nButtons.m_pButtonStates[0..2]`, schema-resolved; in pre they read what the previous command left). The cookbook's `sm_usercmd trace` logs pre vs post origin, tick, command number and commands-per-tick for the live check.
