**Usercmd post phase (2026-11-12) — offline; live acceptance pending.** Prompted by replay recording (EdgeGamers' 3D round replays, surf timers' replay recorders), which needs each player's state after every command. `clients.onRunCmd(handler, { phase: "post" })` and the `OnPlayerRunCmdPost(cmd, info)` export now run once per command the server actually ran, after its movement was applied and written back to the pawn; `"pre"` stays the default and is unchanged. The pre phase hooks the batch entry (`ProcessUsercmds`), which sees every command before any of them runs, so post needed its own engine point: `CPlayer_MovementServices::RunCommand` (new core gamedata `PlayerMovementServices_RunCommand`, unique on builds 26598758 and the Nov 5 one; vtable slot 26 of `CPlayer_MovementServices_Humanoid`, checked by index, with `CCSPlayer_MovementServices` overriding slot 26 with a guard that tail-jumps to it). It is a checked KHook binding installed lazily on the first post subscriber, like the pre one, and the pre install is now per channel too (it used to test whole-store emptiness, which a post subscriber would have defeated). In post the command is read-only twice over: the shim's post frame has no mutable command and core's write natives no-op (a debug build warns once); the handler's return is ignored and does not truncate other subscribers. **Reads are plain memory.** The shim copies each executed command into one `S2UsercmdSnapshot` (moves, view angles, impulse, `legacy_command_number`, held buttons, the movement services' pressed/changed/scroll, slot, server tick) and core publishes it in a region every plugin context holds an `ArrayBuffer` view of (taken once by the prelude, native then deleted), so in post every `UserCmdView` getter and `info` field is a typed-array read with no native call. The shim reads the command at the generated protobuf layout's offsets (new core gamedata `offsets`: `UserCmdPB_base`, `BaseUserCmdPB_*`, `InButtonStatePB_buttonState1`, `MsgQAngle_x`, read off the build's reflection offset tables), but trusts them only after the first 64 commands agree bit-for-bit with reflection and show two distinct non-zero command numbers (`shim/src/usercmd_layout.h`, tested by `scripts/test-usercmd-layout.sh`); any disagreement prints a named gamedata FAIL and the snapshot stays on reflection. A steady-state post dispatch makes no Rust allocation (a test counts them); getting there fixed two allocations every fan-out in core paid per subscriber call: `Registry::is_live` built a `String` key for each liveness check (`LiveTable::is_live` now takes a borrowed key), and `ParentBusy` copied the owner id into a fresh `String` (its stack now reuses popped entries). `UserCmdView` gains read-only `pressedButtons` / `changedButtons` / `scrollButtons` (`CPlayer_MovementServices::m_nButtons.m_pButtonStates[0..2]`, schema-resolved; in pre they read what the previous command left). The cookbook's `sm_usercmd trace` logs pre vs post origin, tick, command number and commands-per-tick for the live check.
