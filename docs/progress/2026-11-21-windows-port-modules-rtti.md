**Windows port W2: PE module images, MSVC RTTI and the first `win64` gamedata (2026-11-21). Fixture-tested and checked against the build-26798866 DLLs, not live-tested.** The production resolver now runs on Windows. `s2original::FromPe` builds the verified original image of a loaded DLL from the file on disk: the loaded headers, section table and CodeView record must match the file's (only the loader's ImageBase rewrite is allowed), executable sections become the original instruction segments, and every readable section is a readable range. The build id is the CodeView RSDS GUID plus age. `OpenLoadedModule` on Windows picks the module the same way as Linux (largest executable section wins), opens it by its wide path, ties it to the volume serial and file index, and reads live data with `ReadProcessMemory`. The image carries its format, and `GetVTableByName` reads MSVC RTTI for a PE image: TypeDescriptor `.?AV<name>@@` (or `.?AU`), then the offset-0 CompleteObjectLocator (its self RVA must agree), then the vftable that points at it, unique or nothing. The by-module overload uses the same path off Linux. Gamedata gains `win64` for every hook slot and layout pin (29 entries, each pin equal to the live RTTI vtable size and each slot derived from the MSVC layout of the SDK header), `GameEntitySystem` 88, and three signatures: `GameEventManager` (lea-disp on the inlined static initializer; MSVC has no separate constructor call), `AddListenerEntity` and `RemoveListenerEntity`. Engine calls through the declarative bridge still refuse on Windows (Microsoft x64 ABI is W3). Plan: `docs/superpowers/plans/2026-11-21-windows-port-modules-rtti.md`.
