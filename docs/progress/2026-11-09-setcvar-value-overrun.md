**Server.setCvar wrote past numeric cvar values (2026-11-09) — offline; live acceptance pending.** Prompted by a CS2 jailbreak server where `Server.setCvar("sv_infinite_ammo", "1"/"2"/"0")` left the engine reporting `-229000626` and grenades stopped running out. `s2_cvar_set` copied a whole `CVValue_t` (16 bytes) into the value slot, but the engine allocates far less: tier0's `RegisterConVar` takes each `ConVarData` from a bump arena as `0x58 + m_ByteSize * slots` (rounded up to 8) and then allocates the cvar's min, max and default values right behind it, in that order (checked in the 2026-11-05 libtier0). `sv_infinite_ammo` registers no min or max, so every int32 write put 8 uninitialised stack bytes (`CVValue_t neu{}` does not zero, because of the union's empty constructor) into the cvar's own default value. The garbage value most likely came from a later reset to that default. For cvars that do have a min or max, the same overrun corrupted the min. `VOFF` (0x58) and the slot stride match the build, and the clamp was not the cause. The fix zeroes the parsed value and copies only `m_ByteSize` bytes (`shim/src/cvar_value.h`). A host test lays out the arena and checks nothing past the slot moves (`scripts/test-cvar-value.sh`, in `ci-native`). `tools/cvarprobe` is the live probe: it compares each `setCvar` against the value and default the engine itself prints on the console.
