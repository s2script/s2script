**Garbage collection diagnostics (2026-11-21). Unit-tested, not live-tested.** A live slow-frame line showed a 6.6 ms full collection under "timers and async results" with 0.1 ms of timer work beside it. The core harness with V8's own trace reproduces it: the full collections of a running server are V8's "finalize incremental marking via task", run by the one-task-per-frame pump (`gc_points`), which the watchdog charged to the async drain. Marking is done in the background (0.1 ms of the pause); the pause is evacuation, the copy of whatever recently allocated memory is still in use, so its length follows what the plugins keep alive from the last few seconds and how many helper threads V8 gets. What allocates on a live server cannot be read from the harness, so this slice adds the tools to read it there. The pump is its own watchdog part, `V8 housekeeping`. `sm prof start js` also runs V8's allocation sampling (inspector `HeapProfiler`, 8 KB interval, collected objects kept), prints the functions that allocated the most with a total and a rate, and writes `prof-<time>.heapprofile`. `S2SCRIPT_V8_FLAGS` passes flags to V8 at start (`--trace-gc`, `--trace-gc-nvp`, or a setting to try such as `--max-semi-space-size`), confirmed by one log line. Harness numbers at 30 plugins and 256 KB of garbage a frame: full pause 3 to 5 ms in every setting tried; young collections up to 6.5 ms by default against 1.3 ms with `--max-semi-space-size=1`, at twice the (small) total. No default changed: the live trace decides which setting, if any, becomes one. Live check: the slow-frame line names `V8 housekeeping` for a full collection; `sm prof start 60 js` lists allocating functions; `--trace-gc` lines appear in the server output.
