# Cookie persistence

`Cookies.set` and `Cookies.setAuthId` return an admission boolean. Check `false` and report or retry the rejected preference change; rejection changes neither cache nor pending persistence. `true` reserves host ownership before changing the cache, including online writes. Disconnect only removes connection cache state and cannot reject or discard a previously accepted write.

The core keeps one outbox for online and offline accounts. Each key retains one immutable leased attempt and at most one newest pending value. Positive int64 revisions and lease IDs cross JavaScript as decimal strings; wall-clock timestamps are display metadata. Count and byte admission includes both retained versions. Unsent writes coalesce while preserving the earliest unsatisfied revision (`covers_from`). Account load fences wait for that obligation, so reconnect SELECTs cannot pass a superseding write that has not committed. Delayed SELECT rows do not replace connection-local dirty entries.

Provisional, injectable core policy (Task 6 will measure and integrate these limits): 4,096 retained versions, 4 MiB retained bytes, 64 KiB per write; charge UTF-8 identity/name/value bytes plus a 128-byte envelope estimate. A pump leases at most four items / 256 KiB, at most one per account. Each live clientprefs generation shares four DB operation slots across reads and writes. Failures return ownership to ready state with monotonic 100ms exponential backoff capped at 5s. Internal `__s2_cookie_outbox_stats()` returns ready/leased versions, bytes, accepted/coalesced/rejected writes, retries and stale ACKs. These are bounded saturating counters. The policy bounds core outbox payloads and live leases/pump submissions, not cache copies, database queues, or measured process RSS. Detached DB actors and their copied inputs can overlap replacement-generation operations transiently after reload. Task 6 must charge those old workers and inputs through actual completion before admitting replacement work; this slice does not claim four actual DB operations across generations.

Owner-store teardown reclaims that plugin generation's leases. Unknown, wrong-owner, wrong-revision and reclaimed ACKs are no-ops. Clientprefs migrates SQLite rows with `writer_epoch` and int64 `revision`, then conditionally upserts only a newer revision in the same epoch. Older detached DB workers therefore cannot replace newer committed values after reload. Equal revision replay is idempotent. The plugin must be the sole cookie-table writer; recipes must not issue unconditional cookie upserts.

Accepted payloads and accounting, writer epoch, revision and lease allocators survive same-process core shutdown/init. Shutdown reclaims leases and clears only connection caches. The allocator is never replaced while detached old actors may run. Full process exit or library destruction loses unacknowledged memory; there is no process-crash durability or bounded shutdown flush guarantee. A fresh process can establish a different writer epoch only after old actors cannot execute. Multiple processes sharing one database are unsupported: differing epochs have no global ordering authority.
