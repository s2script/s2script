# Gamedata tiering — SourceMod's owner/applicability model, ported (A5)

**Status:** Approved — ready for planning.
**Audience:** core/shim maintainers; anyone adding an engine fact or porting s2script to a second
Source 2 game; operators who need to hot-fix a broken signature after a CS2 update.
**Builds on:** `gamedata/core.gamedata.jsonc` + `shim/src/gamedata.{h,cpp}` (the flat loader),
`shim/src/engine_calls.{h,cpp}` + `core/src/gamedata_calls.rs` (the plugin-declared engine-call
path, `docs/superpowers/specs/2026-07-24-plugin-gamedata-design.md`), and
`docs/superpowers/specs/2026-07-30-core-stabilization-audit.md` §A5.
**Reference:** `alliedmodders/sourcemod` @ `master` — `gamedata/` tree and `core/logic/GameConfigs.cpp`.

---

## 1. Goal

Give s2script SourceMod's gamedata organization: **four owner namespaces**, **applicability-selected
files** within each, and an **operator override channel** — then use that structure to move the CS2
API signatures out of core's namespace and into the `@s2script/cs2` game package's, so a
"Valve has a member function, wrap it" slice costs **zero core diff**.

This closes A5 of the core-stabilization program. `defer:"nextFrame"` on `Engine.call` is **not**
part of it — dropped after `#63` (see §9.2).

## 2. The dilemma, and why SourceMod doesn't have it

The question "is this gamedata entry engine-generic or CS2-specific?" has no stable answer.
`CBaseEntity::SetModel` is a Source 2 concept that any game would have — but its byte pattern is
CS2's `libserver.so` and would be regenerated per game. Every entry in
`gamedata/core.gamedata.jsonc` is like this: **all 29 signatures scan `libserver.so`**, the game
binary. A one-axis split therefore either relabels the file without moving the boundary, or empties
core's namespace down to ten interface strings.

SourceMod never asks that question. It answers two *independent* questions with two *independent*
axes:

| Axis | Encoded as | Answers |
|---|---|---|
| **Owner** | the directory (`core.games/`, `sdktools.games/`, `sm-cstrike.games/`) or flat file (`funcommands.games.txt`) | *who consumes this fact* |
| **Applicability** | the file within it (`common.games.txt`, `engine.csgo.txt`, `game.cstrike.txt`) | *what this fact is resolved against* |

`core.games/engine.csgo.txt` is core's own facts, resolved against CSGO's `server` binary. Both
things are true at once and SourceMod finds it unremarkable. That is the whole resolution:
**owner and target are orthogonal.** Adding a second Source 2 game later means adding
`gamedata/core/game.<mod>.jsonc` with the *same key set* and different bytes — exactly
`sdktools.games/game.tf.txt` beside `game.cstrike.txt`.

### 2.1 What SourceMod actually does (verified against the source)

Four mechanisms, not one:

1. **Owner namespace.** A consumer calls `LoadGameConfigFile("sdktools.games")` and gets a
   `GameConfig` scoped to that owner only. Two owners may define the same key with different
   values; neither sees the other's. Today's owners: `core`, `sdktools`, `sdkhooks` (extensions),
   `sm-cstrike` (a *game* extension), `funcommands` / `sm-tf2` (single plugins).
2. **`master.games.txt`** inside an owner directory maps file → condition:
   unconditional, `"engine" "<engine>"`, or `"game" "<moddir>"`. One file may list several
   conditions (`engine.insurgency.txt` claims both `insurgency` and `doi`). Files apply in listed
   order; later overrides earlier. The master is parsed **twice**, for `{base engine, engine}` —
   `GameConfigs.cpp:862-882` — which is how engine inheritance works.
3. **In-file section filter.** `"Games" { "#default" {…} | "<moddir>" {…} }`, and a `#default`
   block may carry a `"#supported"` list of engines/games. A second filter for facts shared by an
   arbitrary set of games that doesn't fall on a clean file boundary.
4. **Operator override.** `gamedata/<owner>/custom/*.txt` is parsed **last**, after every shipped
   file (`GameConfigs.cpp:898-937`); for flat owners, `gamedata/custom/<owner>.txt`
   (`GameConfigs.cpp:843`). Every shipped file's header says *"Do not edit this file."* An
   operator fixes a broken signature by dropping one file in `custom/` — no rebuild, no release.

Fact kinds are `Offsets` (per-platform int, or `class`+`prop` netprop lookup), `Signatures`
(per-platform pattern + `library`), `Addresses` (signature + read/offset chain), and `Keys` —
arbitrary strings, including genuinely *behavioral* ones. `funcommands.games.txt` carries beacon
sprite paths, sounds and per-team colors, with a `"csgo"` section overriding the `#default` set.

## 3. The tree

```
gamedata/
  core/                          # owner: keys named in shim C++ / core Rust source
    master.gamedata.jsonc
    common.gamedata.jsonc        #   unconditional
    engine.source2.jsonc         #   "engine": "source2"
    game.cs2.jsonc               #   "game": "csgo"
    custom/                      #   operator overrides — parsed LAST
  cs2/                           # owner: the @s2script/cs2 game package
    master.gamedata.jsonc
    game.cs2.jsonc               #   "game": "csgo"
    custom/
  custom/                        # overrides for flat single-file owners (SM's gamedata/custom/)

<plugin>.s2sp:/gamedata.json     # owner: one plugin — already shipped, unchanged by this slice
```

Four owner tiers, matching SourceMod's four. The **extension tier** (`sdktools`/`sdkhooks`) is
deliberately left unpopulated: no capability module needs its own namespace yet, and the loader
treats owners uniformly, so adding `gamedata/entity/` later is a data drop.

`common.gamedata.jsonc` ships with a header comment and empty sections — the tier is visible even
though no fact has yet been proven game-independent.

## 4. The ownership rule

**A key belongs to whoever names it in source.** If `shim/src/*.cpp` or `core/src/*.rs` contains
the literal key string, the entry lives under `gamedata/core/`. If nothing in core or shim names
it — it is reached only through a descriptor — it lives under the game package's or the plugin's
namespace.

This is mechanically checkable, which is why it beats "is the concept engine-generic?": a new
`scripts/check-gamedata-owners.sh` gate greps every key in `gamedata/cs2/**` against `shim/src` and
`core/src` and fails on a hit, and greps every key in `gamedata/core/**` for the inverse. It joins
`ci-native.sh` beside the existing boundary/nameleak checks.

The rule has a consequence that defines the slice: **`gamedata/cs2/` is only non-empty once the CS2
ops are retired from core.** As long as `s2script_mm.cpp:4063` reads `sigs.find("Respawn")`,
`Respawn` is core-owned *by definition*. Moving the file without retiring the op would be
relabelling, not a boundary change.

### 4.1 Initial placement, and why it cannot be got wrong

For the 46 entries in today's flat file:

| Destination | Entries |
|---|---|
| `core/engine.source2.jsonc` | the 5 engine-module interface strings: `SchemaSystem`, `EngineCvar`, `EngineToServer`, `NetworkServerService`, `NetworkMessages` |
| `core/game.cs2.jsonc` | 5 interface strings (`Source2Server`, `Source2GameClients`, `Source2GameEntities` — acquired via `GetServerFactory`; `GameResourceService`, `GameEventSystem` — acquired via `GetEngineFactory` like the engine tier's five, placed here conservatively per below), 5 of the 7 offsets, and 21 of the 29 signatures |
| `cs2/game.cs2.jsonc` | the 2 parked `CCSPlayer_ItemServices_*` offsets (A5a) + the 8 CS2-API signatures (A5b) |

Verified empirically: of the 46 entries, exactly 44 are named in `shim/src` or `core/src`, and the
two unnamed ones are the parked `CCSPlayer_ItemServices_*` offsets. The ownership rule therefore
partitions today's file with **no allowlist and no judgement calls**, and A5a can move those two
immediately — which also leaves `gamedata/cs2/` non-empty, so the new tier is exercised by the
loader from its first commit rather than sitting unproven until A5b.

Placement between `engine.source2` and `game.cs2` is **conservative by default**: when in doubt an
entry goes to the game file. This costs nothing, because for CS2 the merged view is identical
either way — the two files differ only in what a *second* Source 2 game inherits. Promoting an
entry from `game.cs2` to `engine.source2` later is a pure data move with no behavioural risk.
Asserting engine-wideness we haven't verified is the only mistake available here, and the default
avoids it.

## 5. File format

Unchanged JSONC, unchanged parser (`packages/sdk/src/gamedata/jsonc.ts` and nlohmann
`ignore_comments=true`), unchanged section shapes. Sections: `interfaces`, `offsets`, `signatures`,
`calls` (plugin-gamedata spec §5), and `keys` (§7). No new resolver strategies — the eight
signatures A5b moves are all `resolve: "direct"`, inside the closed vocabulary.

`master.gamedata.jsonc`:

```jsonc
{
  "files": [
    { "file": "common.gamedata.jsonc" },
    { "file": "engine.source2.jsonc", "engine": "source2" },
    { "file": "game.cs2.jsonc",       "game":   "csgo" }
  ]
}
```

**An array, not an object, and this is load-bearing.** Array order is the apply order, and the
shim parses with plain `nlohmann::json`, whose object type is `std::map` — object keys come back
**alphabetically sorted, not in file order**. A master expressed as an object would have its apply
order silently decided by filename spelling; today's names happen to sort correctly, which is
exactly the kind of accident that breaks on the first file added. An entry may name several
conditions (`{ "file": "…", "game": ["csgo", "csgo_beta"] }`) — SourceMod's repeated-key idiom,
expressed as an array because JSON has no duplicate keys.

**Not ported:** SourceMod's in-file `#default` / `<moddir>` / `#supported` sections (mechanism 3).
The file-level condition covers every case we have, and s2script already carries a per-entry
platform key (`linuxsteamrt64`) that does the same job one level down. If a fact ever needs to
apply to an arbitrary set of games that doesn't split cleanly by file, `#supported` is the proven
answer and gets added then — not now.

## 6. Loader semantics

**API.** `LoadInterfaceVersions` / `LoadOffsets` / `LoadSignatures` stop taking a path and become
methods on an owner-scoped `GameConfig`, built once per owner at Load. Keys never cross owners.

**Detection.** `engine` is a shim compile-time constant `"source2"`. `game` is the mod directory,
derived from the existing `dladdr` chain in `GamedataPath()` (`s2script_mm.cpp:2387-2401`): three
`dirname` steps already reach `addons/s2script`; two more plus `basename` reach `csgo`. No new
engine dependency, correct regardless of the server's working directory, and it degrades to the
same cwd-relative fallback the current code uses.

**Order and granularity.** Files apply in master order (common → engine → game), then
`custom/*.jsonc` in sorted filename order. Later wins, replacing at the **named-entry** level —
`signatures.Respawn` is swapped wholesale, never deep-merged. That is what lets an operator
override be a one-entry file.

**Degrade.** Per-descriptor with a named reason, unchanged doctrine. A missing or unparseable owner
directory disables that owner's entries only and is reported in the boot gamedata banner. A missing
`master.gamedata.jsonc` for an owner is a **named hard error for that owner**, never a silent empty
namespace — the failure mode we are least willing to ship is "everything resolved to nothing and
nobody said so."

**No legacy fallback.** SourceMod keeps the flat-file path for third-party extensions; we do not
need it. Plugin gamedata is packed inside the `.s2sp`, so nothing on disk depends on the old shape,
and `scripts/package-addon.sh` fails the build if the tree is absent.

## 7. `keys` — behavioural strings

SourceMod's `Keys` section is adopted, **restricted to the game and plugin tiers**:

```jsonc
// gamedata/cs2/game.cs2.jsonc
"keys": {
  "SpriteBeam":       "sprites/laserbeam.vmt",
  "SoundBoom":        "weapons/hegrenade/explode4.wav",
  "Team2BeaconColor": "255,75,75,255"
}
```

`gamedata/core/**` carries `interfaces` / `offsets` / `signatures` **only**; a `keys` section there
fails the owner gate. This is what makes an `@s2script/base-funcommands` port across games without
a code fork, and it is exactly why SourceMod has the section.

**This amends a standing guardrail.** CLAUDE.md currently says "behavioral facts and name mappings
in reviewed code." The amended wording: *"Core gamedata carries layout only. Game-package and
plugin gamedata may carry per-game behavioural strings (`keys`) — asset paths, sounds, colours,
tunables — because those are per-game data, not logic. Decision logic stays in reviewed code."*

## 8. A5a — the loader and the tree

Mechanical; no behaviour change.

- `shim/src/gamedata.{h,cpp}`: owner-scoped `GameConfig`, `master.gamedata.jsonc` parsing,
  condition matching, `custom/` merge, moddir detection.
- `gamedata/core.gamedata.jsonc` → `gamedata/core/{common,engine.source2,game.cs2}.gamedata.jsonc`
  per §4.1, comments carried verbatim (they are the treadmill re-resolution recipes).
- `gamedata/cs2/` created and wired, carrying the 2 parked `CCSPlayer_ItemServices_*` offsets
  (§4.1) so the tier is loader-exercised from the first commit.
- `scripts/package-addon.sh`, `scripts/package-release.sh`, `scripts/check-gamedata-sigs.sh`
  updated for the tree; `scripts/check-gamedata-owners.sh` added to `ci-native.sh`.
- Override channel: shipped files get the "do not edit" header; a parsed `custom/` file is logged
  loudly at boot **and** marked in the crash-reporter treadmill fingerprint, so an incident never
  silently attributes an operator's patched signature to a shipped one.

**Gate:** every one of the 46 entries resolves to the byte-identical address/value it resolved to
before the split, asserted at boot and diffed against a captured pre-change banner. No live-gate
behaviour change is expected, so any live-gate movement is a bug in the loader, not in the data.

## 9. A5b — retiring the CS2 ops

Behavioural; needs a live gate.

The 8 keys, each named in one uniform block of `shim/src/s2script_mm.cpp`: `CommitSuicide` (3974),
`ChangeTeam` (3993), `SwitchTeam` (4012), `TerminateRound` (4029), `Respawn` (4063), `SetPawn`
(4089), `GiveNamedItem` (4302), `RemovePlayerItem` (4314). Each becomes a `calls` entry in
`gamedata/cs2/game.cs2.jsonc`; the corresponding `S2EngineOps` field and shim block are deleted;
`games/cs2/js/pawn.js` gains the safe typed wrapper.

The two `CCSPlayer_ItemServices_*` offsets are named nowhere in shim or core — parked entries from
the deferred `dropActiveWeapon` work — and are already in `gamedata/cs2/` from A5a (§4.1).

### 9.1 Blocker — `Respawn` needs a validator the format doesn't have

`Respawn`'s gamedata comment specifies a semantic boot gate beyond signature uniqueness: *the
sig-resolved address must appear among the RTTI-derived primary-vtable function slots, else the
descriptor is disabled* — the unique-but-wrong trap the round-control slice proved real. The
plugin-gamedata format defines exactly one validator, `prologue`. Porting `Respawn` as-is would
**silently drop that gate**.

A5b therefore adds `vtable-member` as a second entry in the closed validator vocabulary:

```jsonc
"target": { "kind": "signature", "name": "Respawn",
            "validate": { "vtable-member": "CCSPlayerController" } }
```

Evaluated shim-side after the `.text`-range check, reusing the existing `s2vtable::GetVTableByName`
RTTI walk. This is the extension the plugin-gamedata spec anticipated deferring (§14), arriving
because a real descriptor needs it rather than on spec.

**Correction, found while planning A5b: there are TWO bespoke gates among the eight, not one.**
`TerminateRound` carries `ValidateTerminateRoundScopeString` (`s2script_mm.cpp:2750`), which exists
for the same reason — *"the borrowed CSSharp/Swiftly sig matches UNIQUELY at the WRONG function on
build 2000875"*. It follows a `lea rsi,[rip+disp32]` at `fn+0xb` and asserts the target is the
literal string `"TerminateRound"`. The other six are uniqueness-only.

So the closed validator vocabulary gains **two** entries, not one. The second generalizes cleanly —
it is ~10 lines reusing `s2sig::ResolveLeaDisp` and `FindModuleBounds`, both already present, and
`lea-disp` is already in the closed *resolver* vocabulary:

```jsonc
"validate": { "string-xref": { "at": 11, "dispOff": 3, "instrLen": 7, "expect": "TerminateRound" } }
```

String-xref is a doctrine-endorsed resolution technique (`docs/re-strategy.md`), so parameterizing
it is a capability the treadmill wants anyway rather than a one-off carve-out. Both validators land
in A5b under the same principle: a validator is added when a real descriptor needs it.

### 9.1b Settled: the two questions A5a's spec left to the plan

**`TerminateRound`'s receiver is an entity with a `via` hop — `receiverless` is not needed.** The
current op is `s2_gamerules_terminate_round(int idx, int serial, int rules_ptr_off, float delay,
int reason)`: it already takes an `EntityRef` (the gamerules proxy) plus a schema offset to the
rules pointer. That is exactly `receiver: {kind:"entity", via:{class, field}}`, and `via` is
live-resolved through the cached `__s2_schema_offset`, so the offset stops being passed from JS.
Args 3 and 4 of the engine function are hardcoded `0` today and stay declared as `int` zeros.

**The game package registers its descriptors over the channel that already exists.** Core's
`gamedata_calls::register_plugin(owner_id, raw_gamedata_json)` (`loader.rs:224`) takes the raw JSON
text and reads both `calls` and `signatures` from it. The shim already hands core the game package
under exactly the right identity — `s2script_core_register_package("@s2script/cs2", js)`
(`s2script_mm.cpp:4870`) — so A5b adds the gamedata sibling of that call, passing the **merged**
JSON the shim's `GameConfig` already produced for the `cs2` owner. Core parses it with `serde_json`
(the shim's nlohmann parse already stripped comments) and registers under `@s2script/cs2`.

This deliberately avoids a second loader: the tree/master/condition/`custom` merge logic stays in
the shim, in one place. Re-implementing it in Rust would recreate exactly the two-implementations
-that-disagree bug A5a hit twice with its JSONC strippers.

`GameConfig` therefore gains the owner's merged JSON as text alongside the parsed sections, and
`@s2script/cs2` is permission-exempt — it is first-party runtime, not a third-party plugin, and no
npm-style plugin id can be spelled with a leading `@s2script/` scope the loader would accept as a
third party. **This is not a privilege change:** the eight natives are unconditionally callable
from any plugin today.

### 9.2 Blocker — the next-frame drains

`Respawn` and `TerminateRound` are drained at the frame boundary in the shim today
(`s_pendingRespawn` / `s_pendingTerminate`), with two properties beyond the deferral itself:

- **dedupe** — a double-respawn in one frame is idempotent (`s2script_mm.cpp:1823-1824`);
- **consume-before-call** — the pending list is cleared before invoking, because the call re-enters
  (`s2script_mm.cpp:5001-5005`).

`defer:"nextFrame"` on `Engine.call` is dropped (SourceMod keeps `SDKCall` orthogonal to
`RequestFrame`; and `#63` proved a re-entrant dispatch cannot be served synchronously at all). So
the deferral moves into `pawn.js` over the existing `nextFrame` — the correct shape — and the
wrapper **must** reproduce both properties. A `Set` of pending refs cleared before the calls fire
is the direct translation. Losing either is a regression of live-gated behaviour, so both get an
explicit live-gate check.

### 9.3 Mechanical remainder

- `SetPawn` + `Respawn` become two sequenced calls in `pawn.js`. No chain primitive is needed —
  JS already sequences.
- `SwitchTeam`'s `team <= 1 → ChangeTeam` fallback and the respawn preconditions move from shim C++
  into `pawn.js`. Behavioural semantics into reviewed code — the doctrine, not a compromise.
- `TerminateRound`'s receiver is game rules, not an entity; it needs `receiver.via` through the
  gamerules proxy, or the `receiverless` path with the rules pointer passed as an argument.
  **Which one is RE work owned by the plan**, not settled here.
- The game package needs a descriptor owner. `core/src/gamedata_calls.rs` keys its registry by
  plugin id; A5b registers `gamedata/cs2/`'s `calls` under a reserved owner key that no npm-style
  plugin id can spell, with the `engine:calls` permission gate bypassed for it. **This is not a
  privilege change:** these eight natives are unconditionally callable from any plugin today.
- `S2EngineOps` loses 8 fields. The struct's per-field comments declare it append-only; A5b
  renumbers and amends that convention to *"append-only across a release boundary, not within
  one"* — core and shim ship in the same zip and nothing external links the table.

**Gate:** the A4 live-gate fixtures plus per-op checks — respawn (including double-respawn-in-frame
idempotence), switchteam both branches, terminate_round, give/remove item, suicide — and a
`vtable-member` negative test (a deliberately wrong signature must disable the descriptor with a
named reason rather than call it).

## 10. Non-goals

- Porting SourceMod's `#default`/`#supported` in-file sections (§5).
- A second game. The tree makes one possible; this slice adds no second game's data.
- The extension owner tier. Structurally available, unpopulated.
- Gamedata auto-updating (SourceMod's updater fetches new gamedata over HTTP). `custom/` gives
  operators the manual channel; a fetcher is a separate future slice.
- `defer:"nextFrame"` on `Engine.call` — dropped, see §9.2.
- Windows platform keys. `linuxsteamrt64` remains the only platform; the key stays explicit so a
  second one is additive.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Loader rewrite silently changes a resolution | A5a's byte-identical gate over all 46 entries, diffed against a captured pre-change boot banner |
| `vtable-member` validator differs subtly from the current in-shim gate | Port the existing RTTI walk verbatim; negative test with a deliberately wrong signature |
| `nextFrame` wrapper loses dedupe or re-entrancy ordering | Explicit live-gate checks for both; the JS `Set` clears before the calls fire |
| `TerminateRound` receiver shape unproven | Called out as plan-owned RE; if neither `via` nor `receiverless` fits, the op stays in core for one more slice and is logged as deferred with its reason |
| `custom/` becomes an unsupportable support surface | Loud boot log + crash-fingerprint marking, so an override is never invisible in an incident |
| Owner gate has false positives (a key string appearing in a comment) | The gate greps the JSON key set against source, and shim comments that mention a retired key are cleaned in the same PR |
