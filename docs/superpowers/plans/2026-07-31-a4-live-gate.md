# A4 live gate — what must be proven before the dispatch chain merges

The A4 chain (#55 → #56 → #57 → #58 → #59 → #60) routes **every** engine→JS dispatch in the runtime
through new code, and changes `Damage.onPre` semantics deliberately. 469 unit tests pass, but they
were written against the *old* code and were not designed to catch what changed.


4. **`docker stop s2script-cs2 && docker start s2script-cs2`** — a `restart` keeps the stale `.so`


## The four checks, in risk order

### 1. First-subscriber engine-op follow-ups install EXACTLY once  ← highest risk

A4f hoisted a whole-store `is_empty()` sample above the `subscribe_into` call for
`s2_usercmd_subscribe`, `s2_entity_listener_on` and `s2_event_subscribe_pre`. Wrong ordering means
the detour/listener **never installs** or **installs twice**, and the mock ops in unit tests cannot
catch either.

**Scoped down before running.** All three installs are idempotent on the shim side —
`Shim_UsercmdHookInstall` early-returns on `s_usercmdHookInstalled`, the `GameEvent` hook request is
guarded by `m_eventHookInstalled` (s2script_mm.cpp:2651), and `AddListenerEntity` guards Find
internally (s2script_mm.cpp:242). "Installs twice" is therefore structurally impossible and only
"never installs" is live-reachable: a sample taken *after* `subscribe_into` makes `first_ever` false
forever and the feature silently dies. So the gate is *does each still fire, for two subscribers*.

**PASS.** Two plugins subscribing all three; counters from `a4_report` / `a4_report_b`:

```
[A4GATE-A#1] REPORT dmg=3 pre=11 post=11 created=1157 runcmd=20210 outputs=1
[A4GATE-B#1] REPORT dmg=2 pre=11         created=1157 runcmd=20650 frames=13978
```

- `Events.onPre` fired 11× in **both** plugins. `pre == post` within plugin A is the discriminator:
  the post subscription reaches JS by a different path, so a double-installed `FireEvent` hook would
  read `pre=22, post=11`. It reads 11/11 — one install, both subscribers served. Still 13/13 after
  the check-3 reload.
- `Entity.onCreate` — 1157 in both, identical.
- `UserCmd.onRun` — fired in both (~20k). **Bots DO generate usercmds**, correcting the assumption in
  "known-unverifiable" below; only usercmd *movement fields* need a human client.

### 2. Damage: `Handled` no longer truncates  ← the deliberate behaviour change

Two plugins both subscribing `Damage.onPre`; the first returns `HookResult.Handled`.

- **Both** handlers must run (this is the B2 fix; previously the second was silently skipped).
- Damage must still be zeroed (block power preserved).
- A handler returning `HookResult.Stop` must still truncate.

Real bullets turned out to be unnecessary: the shim's `S2_DAMAGE_SELFTEST` fires a synthetic
`CTakeDamageInfo` (`m_flDamage=42`) at frames 300/900/1800 of the process, so one cold boot gives
three deterministic dispatches. `a4gate-a` cycles `Handled → Stop → Continue` across them, which
removes the rcon timing race entirely. It registers **two** handlers so their relative order is
registration order (cross-plugin order is not guaranteed); `a4gate-b` supplies the second context.

**PASS.**

```
damage self-test (frame 300)
[A4GATE-A#1] dmg#1 h1 saw=42 -> zeroing, return Handled
[A4GATE-A#1] dmg#1 h2 RAN saw=0          ← Handled did not truncate, and the write landed
[A4GATE-B#1] dmg#1 B  RAN saw=0          ← …across a plugin boundary

damage self-test (frame 900)
[A4GATE-A#1] dmg#2 h1 saw=42 -> return Stop
                                          ← no h2, no B: Stop still truncates

damage self-test (frame 1800)
[A4GATE-A#1] dmg#3 h1 saw=42 -> return Continue
[A4GATE-A#1] dmg#3 h2 RAN saw=42
[A4GATE-B#1] dmg#2 B  RAN saw=42         ← B's own counter reads 2, not 3 — it missed exactly #2
```

B's counter lagging A's by exactly one is the truncation showing up in the totals independently of
the line ordering.

### 3. Plugin reload with live subscriptions  ← fails OPEN if wrong

A4d folded the reload-liveness `generation` token into the handler type (`Descriptor<(u64, H)>`). The
unit test proves the round-trip in isolation; it does not prove a real reload still gates liveness.

- Plugin subscribes several channels, then reload it while events are firing.
- No dispatch into the stale context, no crash, and the reloaded instance receives events.
- Failure mode is silent and dangerous: dispatching into a disposed context.

There is no reload console command — the loader polls `.s2sp` **mtime**, so `touch` on the deployed
file is the reload trigger.

**PASS.** `a4gate-b` holds a per-tick `onGameFrame` subscription and was touched mid-run, with
`onRunCmd` dispatching ~20k times and frames ~14k times:

```
[A4GATE-B#1] unloading (frames=15168 dmg=2)
[A4GATE-B#2] loaded                        ← load counter came through ctx.previous
[plugins] '@a4gate/b' Active
[A4GATE-B#2] onRunCmd FIRED (first)        ← new instance live on a per-tick channel immediately
[A4GATE-B#2] heartbeat frames=512 …
```

Not one `B#1` line after the unload marker, and plugin A was undisturbed throughout
(`pre == post` still held at 13/13 afterwards). The generation token A4d folded into the handler type
gates liveness correctly under load.

### 4. View-backed payloads round-trip

`usermsg`, `usercmd`, `output` had their `build_args` bodies lifted verbatim but run under mock ops in
tests. Confirm a real `UserMessages.onPre` sees correct fields, and `Entity.onOutput` fires with the
right activator/caller.

**PASS for `output` and `usercmd`; `usermsg` NOT covered.**

```
[A4GATE-A#1] onOutput OnTrigger caller=16440 activator=-1 value="" delay=0
```

A runtime `logic_relay` fired through the delayed-input path (see below). Fields are all correct for
a bare `Trigger`: real caller index, no activator, empty value, zero delay. `usercmd`'s view is
exercised by check 1's ~20k dispatches, though only its *presence* — reading movement fields still
needs a human client.

`UserMessages.onPre` was not exercised. It needs a message the bots-only server actually emits, which
is its own scenario; carrying it forward rather than claiming it.

## Gotchas found while running this

- **A server command's `console.log` goes to the rcon reply, not the container log.** `a4_report`
  reads as a no-op if you discard rcon stdout. Work the command triggers *asynchronously* does land
  in the container log.
- **JS-initiated engine work cannot observe its own listeners.** An entity created from JS never
  fires `onCreate`, and an input fired from JS never reaches `onOutput`: core still holds the isolate
  borrow, so the re-entrant dispatch is `try_borrow_mut`-skipped (for every plugin, not just the
  caller). Check 4 works only because `acceptInput(..., delay)` hands the fire to the engine's own
  I/O queue for a later frame. `onCreate` counts are driven by engine-created entities instead.

## Known-unverifiable here

Bots are 100% stationary (no nav data), so anything needing a MOVING player — usercmd movement field
*values*, voice transmit, client console — is not bot-provable. Those need a human client. Bots do
generate usercmds, so the dispatch path itself is provable; only the field contents are not.

## If a check fails

The chain is six PRs deep; bisect by base branch. #55 (`fan_out`) and #56 (`fan_out_collapsing` +
damage) carry the semantic changes; #57/#58/#59/#60 are mechanical. Check 2 failing points at #56;
check 1 at #60; check 3 at #58.
