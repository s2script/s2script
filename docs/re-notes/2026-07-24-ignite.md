## 1. Headline: `CBaseEntity::Ignite` does not exist on this build — it is `CBaseModelEntity::Ignite`

`Ignite` is a virtual introduced at **`CBaseModelEntity`**, not `CBaseEntity`. Proof, from the RTTI
walk (§9 recipe A):

- `CBaseEntity`'s primary vtable (offset-to-top 0) has its fn base at `0x23ccf48` and is
  **237 slots long** (slots 0…236). Slot 237 (`0x23cd6b0`) holds a literal `0` with **no relocation**
  — i.e. it is the `offset-to-top` word of the *next* sub-vtable, and slot 238 (`0x23cd6b8`) holds
  `0x23caac0`, a `type_info` pointer that is **not** in `.text`. The vtable provably ends there.
- `Ignite` lives at **index 264**, which is *past the end* of `CBaseEntity`'s vtable. It first exists
  on `CBaseModelEntity` (fn base `0x23cedd8`, **270** slots) and every descendant:
  `CBaseAnimGraph` (304), `CBaseCombatCharacter` (336), `CBasePlayerPawn` (398),
  `CCSPlayerPawnBase` (411), `CCSPlayerPawn` (412).

Corroborated by name, not just by layout: the only `Ignite` **Pulse API** binding in the binary is
`"CBaseModelEntityAPI::Ignite"` (@`0x9219d2`), sitting in a 0x50-stride descriptor record at
`0x25f5b20` next to `CBaseModelEntityAPI::IgniteLifetime` / `…IgniteHitboxFireScale` /
`…IgniteNumHitboxFires` — the CS:GO `CBaseAnimating` ignite-input family, re-homed onto CS2's
`CBaseModelEntity`. **There is no `CBaseEntityAPI::Ignite`.**

→ Task 9 must write `"class": "CBaseModelEntity"`, never `"CBaseEntity"`. A pawn receiver is fine:
`CCSPlayerPawn` inherits the slot unchanged (§2).

## 2. The resolved target

```
CBaseModelEntity::Ignite        vaddr 0x15cb290   (file 0x15ca290)   vtable index 264
```

**Ship it as a signature (`resolve: "direct"`), not as an index** — Rule 1. The masked prologue,
validated UNIQUE (§3):

```
55 48 89 E5 41 56 66 41 0F 7E C6 41 55 49 89 D5 41 54 41 89 F4 53 48 89 FB 48 83 EC ? 83 E6 04
```

32 bytes, one masked byte: the volatile stack-frame immediate of `sub $0x30,%rsp`. Everything kept is
load-bearing ABI evidence, not incidental register allocation:

| Bytes | Insn | Meaning |
|---|---|---|
| `55 48 89 E5` | `push %rbp; mov %rsp,%rbp` | frame |
| `41 56` | `push %r14` | |
| `66 41 0F 7E C6` | `movd %xmm0,%r14d` | **arg1 is a `float` in `xmm0`** (saved across calls) |
| `41 55 49 89 D5` | `push %r13; mov %rdx,%r13` | **arg3 is a pointer in `rdx`** |
| `41 54 41 89 F4` | `push %r12; mov %esi,%r12d` | **arg2 is a 32-bit int in `esi`** |
| `53 48 89 FB` | `push %rbx; mov %rdi,%rbx` | **`this` in `rdi`** — an entity receiver |
| `48 83 EC ?` | `sub $0x30,%rsp` | masked (frame size drifts per build) |
| `83 E6 04` | `and $0x4,%esi` | the **flags bit-2 test** (see §5 — this is the bit that matters) |

`resolve: "direct"` is correct: the match offset **is** the function entry (the value stored in
vtable slot 264 is exactly `0x15cb290`).

Same-index sanity check across the receivers Task 9 can pass:
`vtable[264]` == `0x15cb290` for `CBaseModelEntity`, `CBaseAnimGraph`, `CBaseProp`,
`CBaseCombatCharacter`, `CBasePlayerPawn`, `CCSPlayerPawnBase`, **`CCSPlayerPawn`** — 240 classes in
total inherit this one implementation and never override it.

## 3. How uniqueness was proven

Two independent scans, both over the **whole 40 MB file** and over the **PF_X segment only**.

**(a) The plan's Step-3 checker, run verbatim** (`docs/…/2026-07-24-plugin-gamedata.md:1117`):

```
$ python3 - <<'EOF'
import re
BIN="/home/gkh/projects/s2script/docker/cs2-data/game/csgo/bin/linuxsteamrt64/libserver.so"
pat="55 48 89 E5 41 56 66 41 0F 7E C6 41 55 49 89 D5 41 54 41 89 F4 53 48 89 FB 48 83 EC ? 83 E6 04"
toks=pat.split(); data=open(BIN,'rb').read()
rx=b''.join(b'.' if t in ('?','??') else re.escape(bytes([int(t,16)])) for t in toks)
print("matches:", len(re.findall(rx, data, re.S)))
EOF
matches: 1
```

**(b) A PF_X-restricted rescan** (the form the boot gate uses) — `whole-file=1  PF_X=1  va=0x15cb290`.

**Margin.** The pattern is not merely *barely* unique; uniqueness arrives well before the end:

| prefix | matches (whole file / PF_X) |
|---|---|
| 6 bytes (`55 48 89 E5 41 56`) | 3406 / 3406 |
| 8 bytes | 27 / 27 |
| 13 bytes | 12 / 12 |
| 16 bytes | 4 / 4 |
| **21 bytes** | **1 / 1** |
| 25 / 29 / 32 bytes | 1 / 1 |

So the shipped 32-byte pattern carries 11 bytes of slack past the first unique prefix — it will
survive a small amount of instruction-scheduling churn before it goes ambiguous, and it fails
**loud** (0 matches) rather than silently wrong if the prologue moves.

**A masked byte cannot have widened the match set**: the sole mask is the frame immediate, and the
unmasked 21-byte prefix (which contains no masked byte at all) is already unique on its own.

## 4. Identity — six independent anchors

`.text`-range + uniqueness prove *an* address; they do not prove *which function*. Per spec §3 (the
ItemServices-slot-24 thunk lesson) the identity is argued separately, and here it is over-determined.
Anchors 1, 2 and 3 are **schema-derived** — they tie the disassembly to field names in our own
regenerable `games/cs2/gamedata/schema-catalog.json`, so they are not guesses.

1. **It fires `m_OnIgnite`.** The function's tail does
   `lea 0x818(%rbx),%rdi; … call 0x21327a0`. `0x818` = 2072 = **`CBaseModelEntity::m_OnIgnite`**
   (`CEntityIOOutput`) in our schema catalog. And `0x21327a0` is not a guess either: our already
   shipped, already live-gated `FireOutputInternal` signature
   (`gamedata/core.gamedata.jsonc:406`) re-resolves **UNIQUE at exactly `0x21327a0`** on 2000877.
   The one function in the binary that fires `CBaseModelEntity::m_OnIgnite` is `Ignite`.
2. **It writes `CEntityFlame::m_hAttacker` from its `rdx` argument.** When `rdx != NULL` the body
   decodes it as a `CEntityInstance*` (`[rdx+0x10]` → `CEntityIdentity*`, `[identity+0x10]` → handle
   index — the same layout `__s2_handle_adopt` uses) and stores the resulting `CEntityHandle` at
   `[rax+0x7a4]`, where `rax` is the entity returned by the flame-creation helper. `0x7a4` = 1956 =
   **`CEntityFlame::m_hAttacker`**. That simultaneously names arg3 (`CBaseEntity* pAttacker`) *and*
   proves the created entity is a `CEntityFlame`.
3. **Its caller passes `CEnvEntityIgniter::m_flLifetime` as arg1.**
   `CEnvEntityIgniter`'s `Ignite` **entity input** (datadesc record at `0x260dce8`: field name
   `"InputIgnite"`, external name `"Ignite"`, handler `0x1847860`) walks target-name matches and, for
   each one that answers non-NULL to the downcast accessor at vtable index 174 (`xor eax,eax; ret` on
   `CBaseModelEntity`, `mov %rdi,%rax; ret` on the combat-character/pawn family — shape-identical to
   Source's `MyCombatCharacterPointer()`, though that name is inference), calls
   `vtable[0x840]` = index 264 with `xmm0 = [this+0x788]`. `0x788` = 1928 =
   **`CEnvEntityIgniter::m_flLifetime`** in our schema catalog. arg1 is the flame lifetime.
4. **The Pulse binding names it.** `"CBaseModelEntityAPI::Ignite"` (§1) lives at `0x9219d2` and its
   descriptor's helper functions (`0x15cb400`, `0x15cb910`) are in the same code neighbourhood as
   `0x15cb290` — same translation unit.
5. **Vtable shape.** Index 264 holds this one address in **240** primary vtables and is overridden in
   exactly **11** — and every one of those 11 is a prop
   (`CBreakableProp`, `CDynamicProp`, `COrnamentProp`, `CPropDoorRotating`,
   `CPropDoorRotatingBreakable`, `CFuncRetakeBarrier`, the `CDynamicPropAlias_*` pair, `CBasePropDoor`
   …). A single base implementation inherited by everything and overridden only by breakables is
   exactly `Ignite`'s expected shape.
6. **A default-argument forwarder points at it.** `0x1628d30` is a 21-byte thunk that loads
   `Vector(FLT_MAX, FLT_MAX, FLT_MAX)` into `xmm2`/`xmm3` and tail-`jmp`s to `0x15cb290`. `FLT_MAX`
   ×3 is Source's `vec3_invalid` sentinel — i.e. the prop override supplies "no position" for
   `Ignite`'s trailing parameter. This is both an identity anchor and the proof of the `Vector` in §4
   below.

Rejected candidates, recorded so nobody re-walks them:

- **`0x1847860`** — `CEnvEntityIgniter::InputIgnite`. A real entity-receiver member, but its only arg
  is `inputdata_t&`, a struct by reference: outside the v1 arg vocabulary (spec §4/§14).
- **`0x18470a0`** — the flame-creation helper (`(CBaseEntity* pTarget /*rdi*/, int /*esi*/,
  float lifetime /*xmm0*/, float size /*xmm1*/) -> CEntityFlame*`; builds the entity through
  `../../game/shared/entityspawner.h:1211`). Tempting — it is 100 % inside the v1 vocabulary and
  would exercise `returns: "entity"` — but it appears in **0** vtable slots and no string names it,
  so I can name its *shape* but not the function. Per Rule 3 I will not invent a name. Left
  unadopted; noted as a future candidate if a `returns: "entity"` demo is ever wanted.
- **The Pulse invoker `0x15cb400`** — Pulse marshalling machinery (walks a global cell table), not
  the method.

## 5. The true ABI — and the one place it exceeds the v1 arg vocabulary

```cpp
void CBaseModelEntity::Ignite( float        flFlameLifetime,  // xmm0
                               uint32       nFlags,           // esi   (bit 0x1, bit 0x4 tested)
                               CBaseEntity* pAttacker,        // rdx   (may be NULL)
                               float        flSize,            // xmm1
                               Vector       vPosition );       // xmm2 = {x,y} packed, xmm3 = z
                                                               //        default vec3_invalid
```

Return type is **`void`**: every exit path is `add $0x30,%rsp; pop…; ret` with `eax` left clobbered
by the preceding calls, and no caller reads a result.

Arg-list derivation, from **four** independent call sites that all agree:

| site | `xmm0` | `esi` | `rdx` | `xmm1` | `xmm2`/`xmm3` |
|---|---|---|---|---|---|
| `0x18478a0` (`CEnvEntityIgniter::InputIgnite`, vcall idx 264) | `m_flLifetime` | `1` | `0` | `0.0` | `FLT_MAX,FLT_MAX` / `FLT_MAX` |
| `0x1637ea4` (devirtualised direct call) | `20.0` | `0` | `0` | `0.0` | same |
| `0x1628d30` (prop override, tail-jmp) | forwarded | forwarded | forwarded | forwarded | **set to `vec3_invalid`** |
| `0x15cb290` itself → `0x18470a0` | forwards `xmm0`, `xmm1`, `esi=1` | | | | |

The trailing `Vector` is passed **by value in an SSE register pair** (`movq` loads 8 bytes = `{x,y}`
into `xmm2`, `movss` 4 bytes = `z` into `xmm3`; the callee reassembles them into 12 contiguous frame
bytes at `-0x40(%rbp)`/`-0x38(%rbp)`). A `const Vector&` would arrive in a GP register — it does not.

> **This is the one spec gap.** v1's `vector` arg is defined as *"passed by address"* (spec §4). An
> SSE-pair by-value `Vector` is **not expressible** in the v1 vocabulary. Do **not** invent a
> `vector` arg for it, and do **not** try to fake it with three trailing `float`s: three declared
> floats would land in `xmm2`(low), `xmm3`, `xmm4`, producing `Vector(f1, 0.0, f2)` — a *valid-looking
> wrong position*, i.e. exactly the silent-misbehaviour class this slice exists to prevent.

**What makes a 4-arg descriptor nonetheless correct on this build:** the `Vector` argument is a
**dead store** in the base implementation. `-0x40(%rbp)` and `-0x38(%rbp)` are written at `0x15cb2b0`
/`0x15cb2b5` and **never read**:

```
$ objdump -d --start-address=0x15cb290 --stop-address=0x15cb3e4 libserver.so \
    | grep -E '\-0x(34|38|3c|40)\(%rbp\)'
 15cb2b0: 66 0f d6 55 c0    movq   %xmm2,-0x40(%rbp)
 15cb2b5: f3 0f 11 5d c8    movss  %xmm3,-0x38(%rbp)
```

Two hits, both stores, across the whole function (`0x15cb290`…`0x15cb3de`, terminated by the
landing-pad `ud2` at `0x15cb3e2`). The position-dependent code path does not exist in this build's
base implementation; the only consumer of the trailing `Vector` is the prop override's own default.
So declaring `args: ["float","int","entity","float"]` calls `Ignite` **correctly** on 2000877 — but
that correctness is a *finding*, not a guarantee, and it belongs in the descriptor's comment so the
treadmill re-checks it (§9 recipe D).

**Arg budget (spec §4).** Integer-class = `nFlags` (`rsi`) + `pAttacker` (`rdx`) = **2 ≤ 5**;
`float` = 2 ≤ 8. Well inside the register budget; nothing spills.

## 6. ⚠️ `nFlags` must be `4`, or `sm_burn` on a player silently does nothing

This is the finding most likely to sink Task 9's live gate, so it is called out on its own.

```
15cb2ad:  and  $0x4,%esi          ; nFlags & 4 ?
15cb2ba:  jne  15cb2d7            ;   set  -> skip the gate
15cb2bc:  mov  (%rdi),%rax
15cb2c4:  call *0x838(%rax)       ;   clear-> call vtable[263] ("is this ignitable?")
15cb2cf:  test %al,%al
15cb2d1:  je   15cb3b2            ;         false -> RETURN, no flame, no output, no error
```

`vtable[263]` — the ignitable predicate — is `0x15bcf00` = **`xor eax,eax; ret` (returns false)** for
`CBaseModelEntity`, `CBaseAnimGraph`, `CBaseCombatCharacter`, `CBasePlayerPawn`, `CCSPlayerPawnBase`
and **`CCSPlayerPawn`**. Only the prop family overrides it (`0x1636e70`).

So `Ignite(10.0, /*nFlags=*/0, NULL, 0.0)` on a player pawn **returns immediately having done
nothing** — a perfectly successful call with no observable effect. That would read at the live gate
exactly like a broken descriptor.

The second gate, reached once bit 0x4 is set:

```
15cb2d7:  and    $0x1,%r12d       ; nFlags & 1 ?
15cb2db:  je     15cb2ef          ;   clear -> skip
15cb2dd:  movzbl 0x5d1(%rbx),%eax ;   set   -> require byte[this+0x5D1] in {1,2}
15cb2e4:  sub    $0x1,%eax
15cb2e7:  cmp    $0x1,%al
15cb2e9:  ja     15cb3b2          ;         otherwise RETURN
```

`+0x5D1` (1489) has **no schema field** — it falls between `CBaseEntity::m_nPlatformType` (1488) and
`m_MoveCollide` (1490), so it is an unexposed enum byte whose live value we cannot read offline.

**⇒ Pass `nFlags = 4`.** Bit 0x4 set bypasses the ignitable gate; bit 0x1 clear skips the
unverifiable `+0x5D1` gate. Both gates cleared, the body then adds effect bit `0x08000000`
(`0xd474d0(this, 0x8000000)`), creates the `CEntityFlame` via `0x18470a0(this, 1, lifetime, size)`,
links it (`0xd4b910(this, flame)`), stores `m_hAttacker`, and fires `m_OnIgnite`.

Semantic reading of the bits, stated as inference not fact: bit 0x4 ≈ *force / skip-ignitable-check*
(what a `sm_burn` admin command wants), bit 0x1 ≈ *require a specific platform/move-type state*. The
engine's own two call sites pass `1` and `0`; neither passes `4`, so **`4` is a value the engine never
uses itself** — worth one sentence in the demo's descriptor comment.

## 8. Bonus for spec §13 — a *real* prologue positive/negative pair

The spec's negative-validation test uses ItemServices slot 24 (a `GiveNamedItem` thunk). This spike
turned up a second, tighter pair inside the *same* virtual, which makes a nicer regression test
because both sides are the same function name:

| receiver class | `vtable[264]` | prologue matches `CBaseModelEntity_Ignite`? |
|---|---|---|
| `CBaseModelEntity`, `CCSPlayerPawn`, … (240 classes) | `0x15cb290` | **yes** — the real body |
| `CBreakableProp`, `CDynamicProp`, `CPropDoorRotating`, … (11 slots, all prop-family) | `0x1628d30` | **no** — a 21-byte forwarder |

`0x1628d30` is in `.text`, is a legitimate vtable member, and is *semantically the same function* —
so `.text`-range validation passes it and only `prologue` tells them apart. Its own masked pattern,
also validated UNIQUE (1 match, whole-file and PF_X), if a negative fixture wants a concrete value:

```
F3 0F 7E 15 ? ? ? ? F3 0F 10 1D ? ? ? ? E9 ? ? ? ?
```

(For completeness: this forwarder *is* fully expressible in the v1 vocabulary — it sets the `Vector`
itself, so `["float","int","entity","float"]` satisfies its entire register contract. It was **not**
chosen as the demo target because it is a thunk bound to the prop family, and enshrining "call a
thunk" as the worked example directly contradicts spec §3.)

## 9. Treadmill re-derivation recipes

Run all four after every CS2 update; each is offline and needs only `objdump`/`readelf`/`python3`.

**A — RTTI vtable-by-name walk** (mirrors the shim's `s2vtable::GetVTableByName`, no symbols needed).
Mangled RTTI name `"16CBaseModelEntity"` → find the `.data.rel.ro` slot holding it (that slot is
`type_info+8`) → find slots holding that `type_info`; the one whose *preceding* qword is `0` is the
**primary** vtable, and function slots start 8 bytes later. Slot values come from the
`R_X86_64_RELATIVE` addends in `.rela.dyn` (the file has no linked-in vtable symbols). Read index
264. Walk the length by following consecutive relocated slots and stopping at the first
non-relocated one — that is how §1 proves `CBaseEntity` ends at 237.

**B — datadesc anchor.** `strings -t x` for `InputIgnite`; find the `.data` slot pointing at it; the
record's external name (`"Ignite"`) is +0x18 and the handler pointer +0x28. That yields
`CEnvEntityIgniter::InputIgnite`, whose `vtable[0x840]` vcall re-derives the index from scratch.

**C — schema anchors.** Re-dump `games/cs2/gamedata/schema-catalog.json` and re-check the three
offsets the identity rests on: `CBaseModelEntity::m_OnIgnite` (2072 = `0x818`),
`CEntityFlame::m_hAttacker` (1956 = `0x7a4`), `CEnvEntityIgniter::m_flLifetime` (1928 = `0x788`). If
the disassembly at the new address still touches all three, it is still `Ignite`.

**D — re-check the two assumptions that are build-specific, not structural.** Both are load-bearing
for the 4-arg descriptor and both are cheap:
1. the trailing `Vector` is still a dead store — `objdump … | grep '(%rbp)'` over the whole function
   and confirm the two SSE spill slots have no reads;
2. `vtable[263]` still returns false for pawns — if a future build makes pawns ignitable, `nFlags`
   could drop back to `0`; if it instead makes bit 0x4 mean something else, `sm_burn` goes quiet.

Then re-mask the new prologue and re-run the §3 checker. **Uniqueness alone is not a green light** —
the `TerminateRound` note in `gamedata/core.gamedata.jsonc` records a borrowed pattern that matched
*uniquely at the wrong function*; re-run recipe C too.

## 10. What this note does **not** claim

Stated explicitly so Task 9 does not over-read it:

- **Not live-verified.** Everything here is static analysis of the on-disk `libserver.so`. The flame
  actually appearing on a pawn is Task 9's live gate, and §6 is the reason that gate could fail with
  no error message.
- **Arg-2 bit semantics are inferred**, not proven: bit 0x4 provably bypasses the ignitable gate and
  bit 0x1 provably enables the `+0x5D1` gate, but the *names* (`force`, `platform-type`) are my
  reading. The byte at `+0x5D1` has no schema entry and its live values are unknown offline.
- **`0x18470a0` is unnamed on purpose.** Its shape (`entity, int, float, float → CEntityFlame*`) and
  its use of `entityspawner.h:1211` are established; its symbol is not. Calling it
  `CEntityFlame::Create` would be a borrowed guess (Rule 3).
- **Nothing was taken from CSSharp / ModSharp / SwiftlyS2 / SourceMod gamedata.** No hint pattern was
  loaded, so unlike `TerminateRound` there is no borrowed-sig false positive to rule out here — but
  the flip side is that there is no third-party corroboration either. The six anchors in §4 are the
  substitute, and three of them are anchored in our own schema catalog.
